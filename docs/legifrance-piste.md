# Légifrance / PISTE connector

## Scope of this phase

LODA collection only (`Fond.LODA_DATE`): Lois, Ordonnances, Décrets,
Arrêtés. JORF/KALI/JURI/CETAT/... are architecturally supported by the
same connector pattern but not implemented — extending `fond`/`natures`
to another collection means validating that collection's own filter
facets and consult route the same way this document did for LODA, not
assuming they're identical.

## Grounding: what was verified, and how

No PISTE Swagger UI was directly reachable in this environment — it
requires a registered PISTE account, which wasn't available. Per the
project's rule ("never guess PISTE endpoints"), two independent real
sources were used instead of guessing:

1. **PISTE's public API catalog** (`piste.gouv.fr/api-catalog-sandbox`,
   checked 2026-08-19, no login required). Confirms:
   - The Légifrance API exists there (version 2.4.2, sandbox, published).
   - OAuth hosts: `oauth.piste.gouv.fr` (production),
     `sandbox-oauth.piste.gouv.fr` (sandbox).
   - API hosts: `api.piste.gouv.fr` (production),
     `sandbox-api.piste.gouv.fr` (sandbox).
   - Swagger 2.0/3.0 specs exist per-API but aren't directly downloadable
     without an account.

2. **[pylegifrance](https://github.com/rdassignies/pylegifrance)** (MIT,
   open source, actively maintained third-party Python client — not
   official DILA/PISTE code). Its
   `pylegifrance/models/generated/model.py` carries this header:
   ```
   # generated by datamodel-codegen:
   #   filename:  legifrance.json
   #   timestamp: 2025-05-28T19:49:07+00:00
   ```
   I.e. it is *mechanically generated* from a real snapshot of DILA's
   OpenAPI spec (`legifrance.json`), not hand-written. Every field name,
   enum value, and endpoint route this connector uses was read directly
   from that generated file and from `pylegifrance/auth.py`/`client.py`
   (the OAuth flow and HTTP call pattern), not invented.

**What this does NOT constitute**: a live test against the real API. No
PISTE credentials were available in this environment, so nothing here was
exercised against an actual HTTP response — only against the (real,
dated) request/response *schema*. Confirm against your own PISTE sandbox
account before production use.

## Endpoints used

| Endpoint | Role | Confidence | Source |
|---|---|---|---|
| `POST {oauth_host}/api/oauth/token` | OAuth2 Client Credentials token | **Host confirmed live** (PISTE catalog); grant flow (`grant_type=client_credentials`, form-encoded, `scope=openid`, JSON response with `access_token`/`expires_in`) confirmed via pylegifrance's real working `auth.py` | Both sources |
| `POST {api_host}/dila/legifrance/lf-engine-app/search` | Full-text/metadata search, `fond=LODA_DATE` | **Well-corroborated**: exact request DTO (`recherche.champs[].criteres[]`, `filtres[]` with `facette`/`dates`/`valeurs`, `pageNumber`/`pageSize`/`sort`/`typePagination`) read from the generated Pydantic models (`SearchRequestDTO`, `ChampDTO`, `CritereDTO`, `FiltreDTO`) | pylegifrance generated model |
| `POST {api_host}/dila/legifrance/lf-engine-app/consult/lawDecree` | Full text of one LODA text version, body `{"textId": <cid>, "date": "YYYY-MM-DD"}` | **Well-corroborated**: request shape from `pylegifrance/fonds/loda.py`'s real call site; response shape (`ConsultTextResponse.articles`/`.sections`, `ConsultArticle.content`, `ConsultSection.articles`/`.sections` recursively) from the generated model | pylegifrance generated model + real call site |
| `GET {api_host}/dila/legifrance/lf-engine-app/consult/ping` | Health check (not wired into this connector yet — see `docs/operations.md`) | Confirmed via `client.py`'s real `ping()` method | pylegifrance |

**Production base path** (`https://api.piste.gouv.fr/dila/legifrance/lf-engine-app/`)
is confirmed (both sources agree). **Sandbox base path**
(`https://sandbox-api.piste.gouv.fr/dila/legifrance/lf-engine-app/`) follows
the same path pattern with the confirmed `sandbox-` host prefix, but the
full sandbox URL was not seen literally in either source — verify it
against your own sandbox account before relying on it.

## Fixtures used in tests

All tests mock `requests.post`/`requests.get` — no test reaches the real
API. Fixtures live inline in `tests/test_legifrance_connector.py` as
Python dicts shaped like the schemas above (search response with a
`results[].titles[]` entry, consult response with nested
`articles`/`sections`), not as separate JSON files, since they are small
and the shapes need close reading in the schema table above to trust.

## Configuration

```json
{
  "environment": "sandbox",
  "keywords": ["cotisations", "contrat de travail"],
  "natures": ["DECRET", "ARRETE"],
  "max_items_per_run": 20,
  "lookback_days_first_run": 7
}
```

`natures` (optional) must be a subset of `LOI`, `ORDONNANCE`, `DECRET`,
`DECRET_LOI`, `ARRETE` (the confirmed `Nature2` enum, LODA subset).
`environment` defaults to `sandbox` — a watch never accidentally targets
production. `fond` is fixed to `LODA_DATE` in code for this phase (not a
config option) since only that collection's schema was verified.

## Credentials

Never set in `configuration_json` or any XML. Read in this priority order
(`services/secrets_service.py`):

1. Environment variables `LKW_LEGIFRANCE_CLIENT_ID` /
   `LKW_LEGIFRANCE_CLIENT_SECRET` (recommended for production).
2. System parameters `legal_knowledge_watch.legifrance.client_id` /
   `legal_knowledge_watch.legifrance.client_secret` (declared empty in
   `data/legifrance_config_parameters.xml` — set the real value manually
   via Settings > Technical > System Parameters, never in a committed
   file).

The **Test Connection** button on a `legifrance` watch calls
`validate_configuration()`, which only checks that a value is *present*
(see "Known limitations" below for why it doesn't go further) — it never
logs, displays, or returns the secret itself in any case.

## What "full text" actually means here

`fetch()` does one `search` call per run, then one `consult/lawDecree`
call **per search result** (bounded by `max_items_per_run`) to get real
article text — not the two-phase "cheap search, then fetch only what
survives local relevance filtering" optimization the broader project
blueprint describes as a nice-to-have. This phase trades a small amount
of PISTE quota for a simpler, uniform `BaseConnector` contract shared with
the RSS connector (no connector-specific two-phase wiring in the
orchestrator). If `consult/lawDecree` fails for one result, that result
still becomes a candidate (title-only, `plain_text` falls back to the
title) rather than being dropped — the failure is recorded in
`source_metadata.consult_error` and logged, matching the PDF-extraction
fallback pattern already used by the manual-import wizard.

## Known limitations / not implemented this phase

- Only `LODA_DATE`. JORF/KALI/JURI/CETAT need their own verification pass.
- No pagination beyond one page per run (`pageNumber` fixed to `1`) —
  `max_items_per_run` bounds each run instead; incremental coverage comes
  from the `since`-date cursor across runs, same idea as the RSS
  connector's ETag cursor.
- `consult/ping` exists (confirmed) but isn't called anywhere yet. Neither
  is a live OAuth token request: **Test Connection** calls
  `validate_configuration()`, which by contract (shared with the RSS
  connector) never makes a network call — it only checks that
  `keywords`/`environment`/`natures` are well-formed and that credentials
  are *present* (env var or system parameter), not that PISTE actually
  *accepts* them. The only way to confirm credentials really work today is
  **Run Now**, which calls `fetch()` and therefore requests a real token.
- No rate/quota tracking beyond HTTP 429 retry-with-backoff — PISTE's
  actual quota policy (requests/day, etc.) was not found in either source
  and isn't enforced client-side.
